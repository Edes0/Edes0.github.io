Summary

A versioned Claude Code configuration: skills, hooks, rules, specs and workflow engines that take a feature from an idea to a reviewed, merged pull request, with guards that keep autonomous agents inside agreed limits. I built it and use it daily at work, and for my own projects.

AI-assisted: agents write much of this code too. I set the design, the rules and the limits, and I review the changes. My standard is that code I reviewed, tested and can explain is AI-assisted programming, not vibe coding.

What I did

  • Started the harness as a versioned set of skills, settings and a statusline, with a morning automation that scouts for upgrades, so the setup is reproducible across machines and keeps up with Claude Code's changes.
  • Built a spec-driven feature sequence — idea, spec, grilling, plan, test-first implementation, landing — with one git worktree per feature and a hand-off to the primary checkout for manual testing.
  • Built autonomous release engines that drive a queue of specs or tracker slices to open pull requests, with an independent looping review, a budget check before each item and a recorded review.
  • Built a severity-aware critic panel for plans, specs and diffs, and a test gym that measures whether it finds seeded defects.
  • Wrote a guard hook and a permission charter that decide, row by row, which agent actions run, ask or are denied.
  • Ported the harness scripts from PowerShell to Python.
  • Built evaluation tooling: a regression suite for skills, harness and model comparisons, and blind judge verdicts.
  • Added work-environment skills: cutting a product release, reading production logs from Grafana, and fetching Jenkins build output.

Outcomes

  • The team workspace is built on it and is used by six people in three departments.

Decisions

One central home for agent config

Per-repository overlays, hooks and settings had spread across repositories. I moved them into one repository with three tiers, so a product repository keeps only its guide and a routing marker. A lint now fails any repository that tracks orchestration of its own.

Every agent loop has three guards

An improvement-finder with no cap ran 12 rounds until the session ran out of tokens, and it never stopped finding "new" items. Every loop now has a hard round cap, stops when nothing serious is left, and stops when a round makes no progress. Stopping on novelty alone is banned, and a cap above the limit is rejected, not raised.

An inline review loop instead of an engine

I compared a deterministic engine with an inline loop on one artifact, once. The engine grew it from 44 to 329 lines, hit its cap and fixed one defect fewer; the inline loop reached 108 lines and converged in 3 rounds. It is thin evidence, but it was enough to delete the engine for this loop.

One charter for every permission decision

A single file decides, row by row, which agent actions run, ask or are denied, and each guard denial names its row. Recursive deletes are judged by where their targets resolve and fail closed. A test goes red when the guard and the charter drift apart.

Replay decides whether an optimisation stays

Cheaper review passes have to reproduce recorded results before they stay. Two did not: batched lenses matched scores much less often, and grouped finders re-found at most 2 of 7 findings against 4 to 5 for the old ones. Both were reverted.

Trade-offs

  • The inline loop's guards are enforced by its specification, not by code: I gained judgment and gave up mechanical enforcement.
  • The guard is best-effort text matching with listed gaps, and bypasses are closed as they are found. It is a backstop, not a sandbox.
  • Rigor in the evaluations is postponed: the regression suite and its rigor pass are still specs, not finished work.

What I'd change

  • Cap every agent loop from the first one, rather than after one ran out the session.
  • Replay an optimisation against recorded results before building it in, rather than reverting it afterwards.
