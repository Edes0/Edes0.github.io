A programmable idle game: players write bots that run around the clock in one shared world. Pre-alpha, over 200 specs, built solo.

Summary

A game I am building to launch. A player writes a bot, by hand or with an AI assistant, and it plays on its own in one shared online world while they watch and tweak it. Its closest references are Screeps, for the persistent world, and Battlecode, for bot matches.

AI-assisted: coding agents write much of the code under checks I set up. I make the design decisions and review every change.

What I did

  • Built the game server in C# on .NET 10, where every bot acts once a second, with pathfinding across rooms, fog of war, economy, building and combat.
  • Built the sandbox that runs each player's bot in its own Docker container with CPU and time limits.
  • Built the Godot client, which only draws what the authoritative server sends.
  • Run it spec-first: feature work starts as a spec and plan and lands as a reviewed pull request with tests.

Outcomes

  • Pre-alpha, with no public world yet. The next goal is a closed demo for 10 to 30 invited players on one hosted world.

Decisions

Bots run inside the tick

An earlier asynchronous design closed a tick before a script's actions arrived, so units stuttered and actions landed late or never. Scripts now run inside the tick and the tick waits for all of them; I rejected a background queue and an overflow buffer. Actions land on time, and the slowest bot sets the length of the tick.

Workers keep world state between ticks

Resending all terrain and fog every tick came to about 2.8 MB per player on an 11 by 11 world, and in a 30-bot run no player's tick met its deadline. A worker now gets terrain once at setup and only the changes after that. I rejected sending only nearby rooms, which would break world-wide pathing. Every language worker must now implement this protocol.

Rooms exist, but only for the server

Rooms started as something players claim. I reversed that: a room is now an internal partition for occupancy, pathfinding and fog of war, and a bot sees one continuous world. Server code may use rooms and player-facing code never shows them.

One client: Godot

I built clients in Unity, Unreal and Godot over the same WebSocket stream. Two live clients meant every visual and wire change was done twice, so Godot became the only one and the others are archived. There is now one client to keep in step with the server, and no browser client.

A bot lives in the player's own folder

A player's code lives in a local folder that the client creates and pushes, and the server never writes back. I rejected activating a starter on the server, which would need a hosted editor, and a folder inside the install, which an uninstall deletes. Git and the editor stay the player's own tools.

Trade-offs

  • The tick is as slow as its slowest bot. Each bot is capped at 150 ms of CPU per tick to bound that.
  • Watching from a browser is given up until a separate viewer exists, because Godot cannot export C# to the web.
  • The server lists 24 languages, but only Python works end to end so far, and the client offers only languages that run.

What I'd change

  • Pick the client sooner, rather than building three.
  • Get one language working end to end before listing the rest.
  • Delete a wrong comment when it is written: stale comments calling rooms obsolete nearly led to a removal costed at over 120 files.
