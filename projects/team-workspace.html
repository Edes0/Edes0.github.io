Summary

A shared workspace that gives colleagues without a personal agent harness the same repositories, skills, guardrails and deploy flow, so they can work with Claude Code on the company's products. I started it alone, on my own initiative, to make other parts of the company work more efficiently, with skills for their daily work that merge with mine.

AI-assisted: written with Claude Code. I designed the workspace and its guardrails, and I reviewed the changes.

What I did

  • Built the wrapper: a manifest of repositories with lazy checkout, and one sparse SVN copy per repository, deepened on demand.
  • Shipped diagnosis, browser-probe and designer skills for colleagues, the last going from images to a live design, a pull request or a ticket.
  • Made it possible to deploy, run and click through a product application locally.
  • Gave agents read-only access to production logs and metrics in Grafana.
  • Wrote a guard hook that gates destructive git, SVN and release commands, asks before customer-data fetches and denies deploys to real servers.
  • Built skills that create a new product application and upgrade one to a later product version, backed by a version map of releases.

Outcomes

  • Used by six people in three departments: development, content and support.

Decisions

A manifest and lazy checkout

The wrapper tracks no product code. It holds a manifest of repositories and checks one out when it is needed, and checkout never resets, stashes, cleans or switches branches, so it cannot destroy a colleague's work.

One sparse SVN copy per repository

Each SVN repository gets one sparse copy, deepened on demand and never made shallower. Read commands go through one call site, and customer data needs explicit confirmation. This replaced full checkouts and a migration path, both now retired.

Separate from my own harness

Colleagues have no personal agent config, so the wrapper carries its own skills and writing guides, and its guard imports nothing from mine. Colleagues get something self-contained; the cost is a second guard to maintain.

Agents do not deploy to real servers

A deploy to a real server is denied, with a reason that tells the person to run it themselves. Customer-data fetches ask first and local deploys are not gated.

Read-only production data through a personal login

A token script was replaced the same day by a hosted connection that signs in as each person, so no shared token is issued or stored. Agents can read logs and metrics while diagnosing a problem.

Trade-offs

  • The guard fails open, so its own failure never blocks anyone's work. The price showed when a colleague's network home drive kept the hook from starting and commands passed unchecked.
  • Some blind spots and false positives in the guard are accepted and documented.
  • Read-only production access rests on the sign-in grant, not on the person's role in the monitoring tool.

What I'd change

  • Run the first version of an integration against the live service before merging it: the token script had run no live query and was gone within hours.
  • Test the guard hook on a colleague's machine early, not only on my own.
